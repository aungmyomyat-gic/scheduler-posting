# AI Agent Instructions — Separate Frontend and Backend Projects

Read `RULES.md` before changing code. This file applies to every AI coding assistant and developer. Scope: the entire repository. More local `AGENTS.md` files may add stricter instructions, never contradict this document.

## Project architecture

- Two independent pnpm projects in `frontend/` and `backend/`. No root workspace, Turborepo, shared runtime package, or cross-project source imports.
- `frontend`: Next.js App Router, TypeScript, Tailwind, feature-based organization.
- `backend`: Express + TypeScript; only backend accesses Prisma/PostgreSQL.
- `frontend/src/components/ui`: shadcn/ui primitives generated by the official CLI.
- `backend/src/contracts` owns the API Zod schemas; frontend boundary schemas must match the reviewed `docs/api-schemas.json` and `docs/contract-fixtures.json`. Tests in both projects enforce the agreement; no runtime dependency between projects.
- `backend/prisma`: Prisma schema, named migrations, and seed tooling, owned by the backend team.
- Server state: TanStack Query; form state: React Hook Form + Zod.

## Mandatory workflow for any task

1. Restate the requested change, its acceptance criteria, and files likely affected.
2. Inspect nearby existing files and patterns before implementing. Do not invent alternate abstractions.
3. If the API contract is missing or ambiguous, propose a typed contract and ask the reviewer to approve it; mock data must conform to the contract.
4. Implement the smallest complete change inside the relevant feature. Avoid opportunistic refactors.
5. Add or update appropriate unit/component tests. For critical flows add end-to-end coverage.
6. Run or explicitly report `pnpm lint`, `pnpm typecheck`, `pnpm test`, and `pnpm build` in EACH project (when available). Never claim checks ran if they did not.
7. Report a concise summary: changed files, assumptions, test results, risks, and remaining TODOs.

## Frontend conventions

- Route handlers, layouts, metadata and page composition in `frontend/src/app`. Business components/hooks/API modules live under `frontend/src/features/<feature-name>/`.
- UI primitives from `@/components/ui/*`; do not duplicate shadcn primitives in each feature.
- Shared frontend utilities under `frontend/src/lib`, not as an unstructured dumping ground.
- Prefer Server Components. Add `'use client'` only for interactive components or client-side hooks; keep client boundaries small.
- Server data required for SEO/initial view: favor server fetching. Client interactions and cached server state: TanStack Query with well-defined query keys.
- Use one typed API client; HTTP access is confined to `features/<feature>/api` and shared `lib/api-client.ts`.
- Keep base URLs in environment variables; never hard-code hosts or secrets.
- Use React Hook Form with Zod for nontrivial user forms. Preserve accessiblity, loading/empty/error/success states.
- Standard naming: folders/files `kebab-case`, React components/types `PascalCase`, hooks `useSomething`, constants `UPPER_SNAKE_CASE`, functions/vars `camelCase`.
- Prefer `type` for data shapes, `interface` when extension is intentional. Do not use `any`, `@ts-ignore`, or unchecked casts without an explained exception.
- Avoid extra libraries unless the senior/reviewer approves and documents the need.

## Backend/database boundaries

- No Prisma client, database credentials, SQL, or privileged backend secrets in `frontend`.
- Don't introduce Next.js API routes as a parallel production backend without an architecture decision.
- Auth credentials must use secure transport and cookie/token policy approved by the senior developer. Don't log credentials/tokens.
- Prisma schema changes require a named migration, review, and compatibility plan.

## Collaboration and AI discipline

- Each ticket has one owner, an acceptance checklist, and defined API/UI contract.
- Work on short-lived `feature/<ticket>-<summary>` branches. No direct changes to protected `main`.
- Prefer one feature per PR, with screenshots for UI changes, test evidence and rollout notes.
- AI agents may not delete migrations, force-push, modify CI/security controls or add dependencies without explicit approval.
- Never fabricate completed tests, working endpoints, UI screenshots or production-ready claims.
- Protect `.env*`, customer data, credentials, API keys, and database dumps.

## Output format for AI task completion

**Summary:** what changed and why.
**Files:** key paths.
**Verification:** exact commands and pass/fail/not-run.
**Assumptions / risks:** contract unknowns, security, migrations, rollout.
**Reviewer notes:** anything requiring senior approval.
