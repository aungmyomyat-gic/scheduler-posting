# API contract

Backend schemas in `backend/src/contracts/` define the transport agreement. Both applications validate the reviewed `api-schemas.json` and `contract-fixtures.json` in tests. No Prisma types are part of the public contract.

## Envelopes

Success:

```ts
type Success<T> = {
  success: true;
  message: string;
  data: T;
  meta: {
    requestId: string;
    pagination?: {
      page: number;
      pageSize: number;
      total: number;
      totalPages: number;
    };
  };
};
```

Failure:

```ts
type Failure = {
  success: false;
  message: string;
  error: {
    code:
      | "BAD_REQUEST"
      | "UNAUTHORIZED"
      | "FORBIDDEN"
      | "NOT_FOUND"
      | "CONFLICT"
      | "VALIDATION_ERROR"
      | "INTERNAL_ERROR";
    fieldErrors?: Record<string, string[]>;
  };
  meta: { requestId: string };
};
```

The backend generates a UUID request ID for each request and sends it in `X-Request-ID` and JSON metadata. All application JSON endpoints use these envelopes. CORS preflight is an ordinary empty OPTIONS response. Liveness does not query PostgreSQL.

## User

```ts
type User = {
  id: string; // UUID, generated by backend
  displayName: string;
  email: string;
  createdAt: string; // ISO 8601 UTC, e.g. 2026-10-29T00:00:00.000Z
  updatedAt: string;
};
```

Editable fields:

- `displayName`: trimmed, 2–80 characters.
- `email`: trimmed, lowercased, valid email, at most 254 characters; unique.
- Unknown body fields are rejected. IDs and timestamps cannot be assigned by clients.
- POST requires both fields. PATCH accepts either/both fields and rejects an empty object. Null values are invalid.

## Endpoints

All paths below start with `/api/v1`.

| Method | Path         | Input                   | Success                                           |
| ------ | ------------ | ----------------------- | ------------------------------------------------- |
| GET    | `/health`    | None                    | 200, `data: { status: "ok" }`                     |
| GET    | `/users`     | Query below             | 200, `data: User[]`, required pagination metadata |
| GET    | `/users/:id` | UUID path parameter     | 200, `data: User`                                 |
| POST   | `/users`     | Editable fields         | 201, `data: User`                                 |
| PATCH  | `/users/:id` | Partial editable fields | 200, `data: User`                                 |
| DELETE | `/users/:id` | UUID path parameter     | 200, `data: { id: string }`                       |

List query:

- `q`: optional trimmed string, at most 100 characters, default empty. Case-insensitive matching on name or email.
- `page`: integer 1–100000, default 1.
- `pageSize`: integer 1–100, default 10.
- Unknown/repeated parameters and non-integers are rejected.
- Sort: `createdAt DESC, id DESC` for deterministic pages.
- `total` counts matching rows; `totalPages = ceil(total / pageSize)`, including 0 when empty. Out-of-range pages return an empty array with the actual total.

```bash
curl http://localhost:4000/api/v1/health
curl 'http://localhost:4000/api/v1/users?q=alex&page=1&pageSize=10'
curl -X POST http://localhost:4000/api/v1/users \
  -H 'Content-Type: application/json' \
  -d '{"displayName":"Practice User","email":"practice@example.com"}'
```

Use the returned ID for detail, PATCH and DELETE requests.

## Error mapping

| HTTP | Code               | Meaning                                                            |
| ---- | ------------------ | ------------------------------------------------------------------ |
| 400  | `BAD_REQUEST`      | Malformed JSON or URL encoding                                     |
| 401  | `UNAUTHORIZED`     | Reserved for a future approved auth integration                    |
| 403  | `FORBIDDEN`        | Rejected browser origin; future auth policy may also use it        |
| 404  | `NOT_FOUND`        | Missing user or API route                                          |
| 409  | `CONFLICT`         | Unique email conflict; includes an email field error               |
| 413  | `BAD_REQUEST`      | Body exceeds the 16 KiB JSON limit                                 |
| 422  | `VALIDATION_ERROR` | Invalid body, UUID, or query; includes field errors                |
| 500  | `INTERNAL_ERROR`   | Unexpected failure, unavailable database, or invalid server output |

`fieldErrors` uses property paths such as `email`; `_form` represents errors on the entire input. Stack traces, request bodies and database error messages are never sent to the browser or printed by the error handler. Unexpected logs contain a request ID and error name.

The frontend API client validates both successful and error envelopes. It creates local `NETWORK_ERROR`, `CONFIG_ERROR`, `HTTP_ERROR`, or `INVALID_RESPONSE` errors for transport/configuration/protocol failures. These are client-side codes, not backend responses. HTTP 4xx queries are not retried; network/5xx queries get one retry; mutations are never automatically retried.

## Changing the contract

1. Agree the request, response, error and UI states with the reviewer.
2. Change backend Zod schemas and frontend boundary schemas together.
3. Run `pnpm --dir backend contracts:export` from the parent folder. Review the JSON schema diff.
4. Update common fixtures, including boundary/normalization cases. JSON Schema cannot describe every custom refinement or transformation; fixtures cover those behaviors.
5. Run both projects' checks and browser tests for affected journeys.

## Initial database migration

`20261029000000_init_users` adds only the User table and its indexes to an empty/new template database. Existing unrelated tables are untouched. Review before applying to any existing database. Emails are normalized by the API before storage; all application writes must pass through it.

For a code rollback, stop the new application and retain the data/volume while deciding compatibility with the previous version. There is no automated destructive rollback, reset, or table deletion in the setup scripts.
